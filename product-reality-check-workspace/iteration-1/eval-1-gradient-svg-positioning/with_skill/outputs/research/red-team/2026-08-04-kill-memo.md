## 3. The single load-bearing fact — CHECKED

### What I picked, and why

The candidates offered were the 186 count, the 90-vs-44,032 comparison, the measured cache HIT, and the
355 count. I checked all four (§5B) — three are exact. But none of them is the true load-bearing fact,
because the package itself designates one:

> ### What survives — the moat, narrowed and true
> > **It moves, and there are 186 distinct effects behind it.**
> — `positioning.md`, "The corrected moat"

That is *one sentence with two clauses*, and it is everything the package has left after retiring
"largest." Every downstream artifact leans on it: the positioning statement, both elevator pitches, the
objection table, the approved README hero. **So I verified both clauses.** Both fail — one factually,
one arithmetically.

---

### Clause 2 — "186 distinct effects": **168**

The count is real as a count of *strings*, and I confirmed it exactly:

```
TOTAL TEMPLATES: 355   UNIQUE NAMES: 355
DISTINCT gradientType VALUES: 186
gradientMapping KEYS: 186   DISTINCT FUNCTION OBJECTS: 186
```

So at the registry layer the package's arithmetic is correct, and I want to be fair about that: 186 is
not invented. But 52 of those 186 mapping entries are inline stubs of the form
`() => ({ useAdvancedEffect: true, effectType: 'X' })`, which do no rendering — they defer to a `switch`
in `src/utils/advancedEffectGenerator.js`. **That switch aliases.** From the source, verbatim, comments
and all:

```js
case 'turbulentWaves':        return generateTurbulentWavesEffect(colors, duration, text);
case 'electromagneticWaves':  return generateTurbulentWavesEffect(colors, duration, text); // 暂时复用湍流效果
case 'auroraWaves':           return generateTurbulentWavesEffect(colors, duration, text); // 暂时复用湍流效果
case 'soundWaves':            return generateTurbulentWavesEffect(colors, duration, text); // 暂时复用湍流效果
case 'cryogenicWaves':        return generateTurbulentWavesEffect(colors, duration, text); // 暂时复用湍流效果
case 'solarWaves':            return generateTurbulentWavesEffect(colors, duration, text); // 暂时复用湍流效果
```

暂时复用 = **"temporarily reuse."** Twelve such comments exist: 5 collapse onto
`generateTurbulentWavesEffect`, 5 onto `generatePortalDistortionEffect`, 1 onto
`generateLiquidMorphingEffect`, 1 onto `generateCosmicMorphingEffect`.

This is doubly damning for the package because `fluidDynamicsGradients.js` **does** contain six
genuinely distinct implementations — `createSolarWavesGradient` builds a radial gradient with three
animated flare paths, `createTurbulentWavesGradient` builds a turbulence filter and a morphing wave
path. They are real, different, and **never reached**. Anyone auditing by reading source files, as the
package did, sees six effects. Anyone auditing by rendering sees one.

I rendered. All 186 types, identical text, identical colours `['ff0000','00ff00','0000ff']`, through
`generateGradientSVG` — the exact function `/api/svg` calls:

```
DISTINCT outputs (raw)             : 168
DISTINCT outputs (ids normalized)  : 168

COLLIDING GROUPS (byte-identical SVG):
  [6] turbulentWaves, electromagneticWaves, auroraWaves, soundWaves, cryogenicWaves, solarWaves
  [6] portalDistortion, hypercubeProjection, wormholeEffect, fractalDimension, multiverseOverlap, realityDistortion
  [4] bioDigitalMerge, quantumDNA, cyberSymbiosis, digitalGenome        ← NOT annotated
  [4] dimensionalTear, holographicGrid, voidDistortion, astralPlane     ← NOT annotated
  [2] liquidMorphing, bioMorphing
  [2] cosmicMorphing, quantumMorphing
```

Direct confirmation: `generateGradientSVG(turbulentWaves) === generateGradientSVG(solarWaves)` → `true`,
2164 bytes. `portalDistortion === realityDistortion` → `true`. `bioDigitalMerge === digitalGenome` →
`true`, 5507 bytes. Control: `horizontal === vertical` → `false`.

**186 → 168. A 9.7% overstatement, of which 6 collisions are not even documented in the source.**

Two further defects the render surfaced that source-reading could not:

- **18 of 186 gradient types emit literal `#undefined` into the SVG** when given three colours — e.g.
  `values="#0000ff;#undefined;#0000ff"`. Confirmed live:
  `GET /api/svg?text=KillMemo&gradientType=turbulentWaves&color0=ff0000&color1=00ff00&color2=0000ff`
  returns an SVG containing `undefined`. Zero of the 355 *shipped templates* hit it (they supply
  enough colours), which is exactly why a template-level audit misses it — it is reachable only
  through the public API the package is positioning.
- **10 of the 186 template `gradientType` values are absent from `gradientMapping` entirely**
  (`ellipse`, `square`, `shimmerBadge`, `terminalTyping`, `skillPills`, `shimmerBanner`, `shimmerText`,
  `goldBadge`, `socialBadge`, `repoCard` — 40 templates), routed instead through a second registry.
  `createGradient()` has a silent `return basicGradients.createHorizontalGradient(...)` fallback for
  anything unmapped. The dual-dispatch means "which number is real" cannot be answered from either
  registry alone — only by rendering.

### Clause 1 — "It moves" / "capsule-render's output is static by default": **false as stated**

The package asserts this with a `[PAGE]` marker — its own notation for *fetched and read*:

> **Output is static SVG by default**; the `animation` parameter applies CSS animation to *text*, not
> the background `[PAGE]`

I fetched all fifteen types from the live capsule-render API and counted
`repeatCount="indefinite"` — the SVG attribute that means "loop forever," as distinct from the
one-shot `animation: fadeIn 1.2s ... forwards` intro every type carries:

| type | indefinite loops | | type | indefinite loops |
|---|---|---|---|---|
| wave *(default)* | 0 | | **waving** | **2** |
| egg | 0 | | **venom** | **1** |
| shark | 0 | | **blur** | **6** |
| slice | 0 | | **pulse** | **4** |
| rect | 0 | | **checkered** | **4** |
| soft / rounded / cylinder / speech / transparent | 0 | | | |

**5 of 15 types animate their background indefinitely.** Sample from `type=pulse`, unmodified:

```xml
<animate attributeName="r" values="47.6;61.6;47.6" dur="4.5s" repeatCount="indefinite"/>
<animate attributeName="opacity" values="0.05;0.12;0.05" dur="4.5s" repeatCount="indefinite"/>
<animateTransform attributeName="transform" type="scale" values="1;1.2;1" dur="4.5s" repeatCount="indefinite"/>
```

Animated radius, animated opacity, animated scale transform — on background circles, not text.

What survives and what does not:

- ✅ **"static *by default*"** is literally defensible: `type=wave` is the default and has 0 loops.
- ✅ The verbatim-locked comparison line's hedge — *"its banners are **mostly** static"* — **survives**
  at 10/15. Credit where due: that sentence was written carefully enough to withstand this.
- ❌ **"capsule-render's output is static SVG by default"** as the general characterization in the moat
  section — fails. A reader picking any of five named types sees motion.
- ❌ **"this is a *category* difference, not a degree difference"** — **flatly false**, and this is the
  load-bearing half. It is precisely a degree difference: 5 animated-background types against 168.
- ❌ **"A reader confirms this by loading two URLs side by side"** — the package's own five-second
  verification test is the mechanism by which the pitch gets caught. It nominated the check that fails it.

**And the package wrote down this exact condition and then filed it as a future risk:**

> 2. **capsule-render ships animated backgrounds.** Deletes the "it moves" moat entirely, leaving only
> the catalogue. *Watch its releases monthly.*
> — `positioning.md`, "What would change this positioning"

It does not need watching monthly. It is true today, and it cost one `curl`.

### Verdict on the load-bearing fact

The moat sentence is *"It moves, and there are 186 distinct effects behind it."* Clause 1 is false as
stated and true only in a hedged form the moat section does not use; clause 2 is 168. **Both halves of
the single sentence the package designates as everything-that-survives were checkable this session, and
neither was checked.**

The generative error is one sentence long: **the package audited the manifest, not the artifact.** It
counted declarations in a registry and read a competitor's README, and never rendered either product.
Every finding above came from running the code — and the code is MIT, local, and takes twenty lines of
Node to interrogate.

That matters more than the 9.7% because of how the package sells the number:

> **"186 distinct effects, and here is the breakdown"** — a *number with its decomposition attached*.
> Strictly stronger than "largest", because it is falsifiable, it survives an audit, and publishing the
> unflattering 20%-are-palettes split is what makes the other 80% believable.

It has not survived an audit. It survived a `new Set()`. A founder who publishes "186, and here is my
honest breakdown" and is then shown 168 and twelve source comments reading *"temporarily reuse"* is in a
**worse** position than one who published nothing — because he will have staked his credibility
explicitly on having already done the audit. The package's own thesis is that being caught inflating a
number costs more than the number was worth. It is right, and it built the trap it describes.

## 4. The three numbers that would change my mind

Two of the three disagree with the package's own priorities. Stated plainly.

### Number 1 — **Distinct third-party accounts: 9 → ≥ 60 within 90 days of a real push**

*Measure:* `gh api search/code -f q='"gradient-svg-generator.vercel.app"'`, count **distinct owners
excluding ChanMeng666**. Today: 9. *Push:* one Show HN, one r/github post, one PR into
`awesome-github-profile-readme`, dated and logged. *Threshold:* ≥ 60 distinct accounts at day 90.

**Accounts, never files.** One account (`TayyebaSadaq`) holds 9 of the 17 third-party files — 53%. A
files-based target is gameable by one enthusiast and the package's own decomposition proves it.

**Where I disagree with the package:** its falsifier is *"if third-party embeds have not moved from 9 by
2027-02-04 (two quarters)"* — passive, six months, no intervention specified. Six months of no
deliberate action tests nothing; it re-measures the last nineteen months. Force the intervention, then
read at 90 days. Under 20 accounts after a genuine push and the diagnosis moves from *obscurity* to
*indifference*, which no positioning document addresses.

### Number 2 — **90-day embed retention: unmeasured → ≥ 70%**

*Measure:* snapshot today's third-party embedding files by SHA; re-query at +90 days; count how many
still carry the URL. *Threshold:* ≥ 70% retained.

**The package never asks this question in any of the four documents.** It counts adoption and never
survival. It is the only number that separates "a novelty people try" from "a thing people keep," and
for a decoration product it is *the* question — the failure mode isn't that nobody adds the banner, it's
that they add it, look at their README a week later, and quietly delete it. Below 50% retention, the
distribution plan is refilling a bucket with a hole in it and every other recommendation is moot.
Above 70%, the obscurity framing is vindicated and worth real effort.

### Number 3 — **Honest, post-fix distinct animated renderers: ≥ 150**

*Measure:* after (a) resolving the 12 `暂时复用` aliases + 6 undocumented collisions, (b) fixing the 18
types emitting `#undefined`, and (c) removing the 22 non-animating types from any "animated" count —
re-run the render-and-hash. *Threshold:* ≥ 150 genuinely distinct, genuinely animated renderers.

Today the defensible figure is **168 distinct, of which 22 types don't loop** → ~146 distinct animated
renderers, before anyone argues about perceptual similarity. That is still an order of magnitude past
capsule-render's 5 animated types and it is a real number. **If a strict recount lands below ~120, the
inventory argument is dead even as the precision fallback**, and what remains is "one URL, no install,
no account" — which is capsule-render's pitch word for word, from a maintainer with 1/300th the
distribution and 1 fork against 731. At that point there is no differentiation to position and the
portfolio-piece verdict is not a judgment call, it is arithmetic.

**certainty**, in three places:

1. **`product-diagnostic.md`, executive summary:** *"the load-bearing numbers in this project **are**
   true and conservative (see F6), and they do not deserve to be discounted."* Stated flat, no hedge,
   in the summary. It is the claim I killed in §3. The whole executive framing — "his stated facts are
   decorative, and that's unfair because the real numbers are honest" — inverts if 186 is 168.
2. **`positioning.md`:** *"It becomes correct at ~10,000 users; it is a liability at 9."* The 10,000

### 5C. The moat under its own logic

The package's structural weakness is a **single sentence pointed in two directions**, and it never
notices:

> **You pay** nothing, ever. It is MIT-licensed and you can host it yourself if you'd rather not depend
> on someone else's URL. — `positioning.md`, the statement
>
> the product is **MIT-licensed and self-hostable**. A buyer asked to pay can fork it and deploy it …
> **A free substitute that is the same software caps the price at zero.** — `monetization-verdict.md`, Archetype A

These are the same fact. In `positioning.md` it is the closing strength — *"converts this product's
biggest structural weakness … into a statement of confidence."* In `monetization-verdict.md` it is the
structural reason revenue is impossible. Neither document cites the other on it. The package is
recommending that the founder **market the property that makes the product unmonetizable**, and
because the two conclusions live in different files it never has to reconcile them.

That is defensible on its own — you can rationally choose reach over revenue. **What is not defensible
is that it isn't differentiating.** capsule-render's README, above the fold, in an `[!IMPORTANT]` callout:

> *This service is provided on a best-effort basis and may be unstable due to usage limits or traffic
> spikes. For reliable use, please **fork** the repository and deploy it to your own Vercel instance.*

The incumbent already makes this exact offer, more prominently, and **731 people took it**. This project
has **1 fork**. So the package's "statement of confidence" is table stakes the market leader states
louder, and the honest-limitation answer it locks verbatim — *"MIT-licensed, so fork it and deploy your
own in about ten minutes"* — is capsule-render's own disclaimer, arriving second and quieter.

### 5H — the live defect nobody in the package found

Recorded here because it is the most actionable finding of the session and appears in none of the four
documents.

**24 of 355 templates are non-deterministic**: `Math.random()` is called at render time in
`advancedEffectGenerator.js` and `templateUtils.js` (22 call sites). The same URL returns different
bytes on every invocation. Verified against **production**, cache-busted:

```
run 1: bytes=7623 sha=ad5346b91cbc2cd8
run 2: bytes=7623 sha=c4d71f56f2403f97
run 3: bytes=7627 sha=0c69bf98d711e30f
run 4: bytes=7621 sha=4887c15f1070ae39
   GET /api/svg?text=Determinism&template=cyber-punk-noir
```

Affected: `cyber-punk-noir`, `neon-grid-city`, `ai-consciousness`, `thought-waves`, `dream-logic`,
`reality-glitch`, `brand-hero`, and 17 others.

Now compose that with `svg.ts:22` — `Cache-Control: public, max-age=31536000, immutable`:

- Two readers of the same README see **different banners**.
- Whichever random variant a reader's browser caches first is **frozen for one year**.
- The CDN caches one random sample **per PoP**, so the banner differs by continent.

The diagnostic's F1 correctly flags `immutable` — but only as *"you can never fix a rendering bug."* The
sharper consequence is that for 24 templates **the endpoint is not a pure function of its URL, and
`immutable` is caching a coin flip for a year.** F1's recommended fix (`s-maxage` + `stale-while-revalidate`)
does not address it; the render must be seeded from the URL.

And the irony is exact: **`svg-parity.test.ts` mocks `Math.random()` with a seeded LCG.** The harness
built to guarantee byte-parity for embedded URLs is mocking away the precise source of byte-instability
in production, and therefore passes green while production is unstable. That is a genuinely interesting
bug, it is a one-line fix (seed the PRNG from the query string), and it is the kind of finding the
package's stated method — *"read as a hostile outsider would: the code that makes each promise"* — should
have produced. It didn't, for the same reason the 186 didn't: **nothing was rendered.**
